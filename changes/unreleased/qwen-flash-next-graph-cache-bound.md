## Bug fixes

- Qwen3.8-Flash-Next no longer grows without bound while it decodes several streams at once. Every decode window and MTP draft chain used to be captured into a CUDA graph that was kept for the life of the process. A graph holds about 1,300 kernel nodes and took 7.4 MiB of unified memory, and four concurrent chat streams met a new window shape in most rounds (4,252 distinct shapes in 7,050 windows), so a node lost 14.3 GiB of available memory in 82 seconds until the memory guard stopped the server. The caches are now bounded (384 window graphs, three per window when the window is split in parts, and 64 chain graphs, tunable with `REXL3_FN_WINDOW_GRAPHS` and `REXL3_FN_CHAIN_GRAPHS`; the least recently launched graph goes first, after the stream has drained), and a shape is captured only when it comes back soon after its first sighting, so a shape seen once runs eagerly and costs no capture and no memory. Replies are byte-identical, also in a benchmark run with only four window and two chain graphs that retired 5,658 graphs. Over twenty minutes of four concurrent streams at temperature 0.6 the node's available memory settled 1.2 GiB below its start with 128 window graphs and 2.3 GiB below with 384 (the 256 extra entries cost about 1.05 GiB) and then moved by 3 to 5 MiB a minute; single-stream decode is unchanged (70.0 tok/s, median of four runs, against 70.1, measured with 128 window graphs) and the four-stream aggregate rises from 100.7 to 107.6 tok/s.
